# useEffect ページのメモ

## 1 デモ 1 文の狙い

| デモ | useEffect の何を見せているか |
|---|---|
| DOM イベントの購読 | 繋ぐ（setup）と切る（cleanup）が対で動き、やめたあとに影響が残らない |
| タイマー | 依存配列は「いつ繋ぎ直すか」の指定で、「いつ処理を走らせるか」の指定ではない |
| データ取得 | cleanup は後片付けだけでなく、進行中の作業の取り消しも担う |

## 判断の記録

- 説明文は「確かめ方」と「見えるはずのこと」に分けた（`shared/ui/HowTo.tsx`）。
  観測値の増減から書き始めると useState の話になってしまい、useEffect の性質が主語にならない。
  購読デモなら「増える」ではなく「**停止後に増えない**ことが cleanup の証拠」が先に来る。
- タイマーデモは当初「一時停止してもタイマーは動き続けている」と書いていたが、画面には
  「タイマーの状態: 一時停止中」と出ていて矛盾していた。文章ではなく **UI を直し**、
  `setInterval` の発火回数を画面に出して、止まっているのが「カウントの加算」だけだと
  目で見えるようにした。ラベルも「カウントの加算」「カウントを止める」に変えた。
- その副作用として、一時停止中も毎秒 state が変わるので再レンダーが続く。以前は
  `previous.paused ? previous : ...` で同じオブジェクトを返し、React の更新バイパスを
  起こしていた。その小ネタは失ったが、「setInterval は生きている」を見せる方を取った。
- ログは React の外（`shared/observability/logStore.ts`）に置いた。Context + useState だと、
  effect からログを書くたびにデモ自身が再レンダーされ、依存配列なしの effect を書いた瞬間に
  無限ループになる。
- データ取得の「読み込み中」は state に持たず、要求中の id と結果の id の比較で導出している。
  effect の中で `setStatus('loading')` すると oxlint の `react(set-state-in-effect)` に当たる。
- レンダー回数を `useRef` の加算で数える案は oxlint の `react(refs)` に当たったので捨て、
  観測したい値を state で素直に数える形にした。

## 実測で分かったこと（StrictMode）

- **StrictMode は `<StrictMode>` をルートに置いたときしか、初回ロードで二重実行しない。**
  `DemoHarness` の中に `<StrictMode>` を置いていたときは、ページを開いた直後のマウントだけ
  二重実行されず、「再マウント」やトグル操作のあとは二重実行された。
  実測ログ（nav → reload → ログ読み取り）で再現を確認。原因は React 内部の挙動で未確認。
  対策として StrictMode を `main.tsx`（ルート）へ移し、トグルは sessionStorage に書いて
  ページを読み込み直す形にした（`shared/observability/strictModeSetting.ts`）。
- **二重実行が起きるのはマウントのときだけ。** 購読の ON / OFF のように依存配列が変わって
  effect が張り直されるときは、StrictMode が有効でも setup と cleanup は 1 回ずつ。
  これを「1 回の購読開始で 2 回ずつ出ます」と書いていたのは誤りだった。
